The Two Trees

Every database keeps its data in one of two machines. Grow both with your own hands and watch where each one pays.

The story (from the lab's README): Kabir files invoices all day and must find any of them instantly. Sorted order makes finding cheap but makes every insert expensive — so there are exactly two famous escapes: the filing cabinet (small sorted pages with slack; a full page splits — the B-tree) and the inbox tray (pile writes up in memory, flush them as immutable sorted files, merge later — the LSM-tree). Machine 1 lets you grow the cabinet; Machine 2 runs the tray. Both are deterministic: Step back replays history to any point.

Machine 1 — grow a B+ tree, watch it split

Pages hold at most 4 keys (real pages hold hundreds — the logic is identical). Top box = root, middle boxes = signpost pages routing by separator keys, bottom row = leaves holding the data, chained left→right. Insert keys and watch: a full leaf splits, promoting a separator upward — and when the promotion reaches a full root, the root itself splits and the tree grows a level from the top. That is the only way it ever gets taller, and why it never needs rebalancing.

Machine 2 — the LSM floor: tray, log, shelf

Writes go to the write-ahead log (crash insurance) and the memtable (the sorted tray in RAM). At 6 entries the memtable flushes to the shelf as an immutable sorted file — an SSTable, newest on top. Files are never edited: an overwrite just shadows the old value, and a delete writes a tombstone. Reading races top-down: memtable first, then each file — unless its bloom filter says “definitely not here” and the file is skipped. Compact merges the shelf into one file, dropping shadowed values and tombstones. Watch the disk-bytes counter: it only ever grows on writes — and shrinks only when you compact.
