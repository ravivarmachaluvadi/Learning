The Query Shape Machine

Every database is an opinionated bet on one access pattern. This page trains the skill of matching a workload's query shape to the store whose bet fits it.

The story so far (from the lab's README): Chaptr, an online bookstore, started on one PostgreSQL database — the right first move. Then growth sent it new shapes of question: a dashboard scanning 40 million rows, a search box expecting typo-tolerant ranking, a view-counter taking hundreds of writes a second, a recommendation query joining orders to orders to orders. Each broke the single store in a different way. Your job on this page: diagnose workloads the way Chaptr's engineers had to.

    Machine B — B-tree vs LSM-tree, thirty-two writes

    The same 32 writes hit both engines. Left: a B-tree (sorted pages; each write lands in place in the page owning its key — red outline = the page being touched; a jump to a different page than last time is a disk seek). Right: an LSM-tree (writes fill a RAM buffer — the dashed box; every 8 writes it flushes to disk as a sorted run, and 4 runs compact into one — all sequential writing). The counters are the cost that matters on spinning disks and still matters on SSDs: seeks vs sequential blocks.
