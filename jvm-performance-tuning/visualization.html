Three ways a perfectly working measurement tells you a lie
None of these involve a bug. In each case the tool reports exactly what it was built to report — and what it was built to report is not the question you were asking. This tab uses the run currently loaded in tab 1, so run something there first for live numbers.

Lie one — the average

A dashboard showing average response time. Each bar is how many of the last few hundred requests fell into that time band. The average sits where you'd expect. The problem is that nobody experiences the average.

Lie two — the stopwatch started too late

Two timers on the same requests. The left one starts when the handler picks the request up. The right one starts when the request actually arrived. When there is a queue, or a pause, these are not the same number — and only one of them is what a person waiting outside experienced.

What this page is, and what it is not

Everything here runs inside your browser. There is no Java process anywhere. What you are driving is a small simulator built from stated rules — so its ratios and shapes are worth learning from, and its absolute millisecond values are not real measurements of any JVM. The rules are printed below in full so you can check every number the page shows against them.

Deliberately not modelled: class loading and metaspace, on-stack replacement, deoptimisation storms, biased-locking revocation, NUMA effects, page faults and swap, disk and network variability, TLB and cache hierarchy, connection-pool limits, downstream services that themselves queue, and the operating system scheduler's own decisions. Each of those has produced a real production incident; none of them is here. The lab's README lists what each one looks like when it is the answer.
