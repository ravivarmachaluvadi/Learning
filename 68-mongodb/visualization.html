The Order Book — what happens to an acknowledged write

Three MongoDB replica-set members keep the same oplog. Every write becomes an oplog entry stamped ts (time) and t (term). The green line is the majority commit point: everything at or below it is on a majority and can never be rolled back; everything above it is one machine's opinion. One tick = one heartbeat = 2 seconds. Election timeout = 10 s (5 ticks), as in the defaults.

Rules the simulator follows

show
  • A secondary pulls missing entries from a reachable node that is ahead (the primary if it can see it; otherwise another secondary — chained replication). One tick of delay per hop.
  • w:1 acknowledges as soon as the primary has applied the write. w:"majority" acknowledges only when the commit point reaches the write. Default wtimeout here: 5 ticks; timing out does not undo the write.
  • The commit point is the highest optime that the primary can see on a calculated majority of voting, data-bearing members (itself included), and only advances over entries from its own term.
  • A member that has not heard from a primary for 5 ticks and can reach a majority of voters and has the highest optime it can see calls an election (term + 1). A primary that cannot see a majority steps down after 6 ticks (its own timer fires one heartbeat later — a deliberate simplification so the stale-primary window is visible).
  • A member whose oplog diverges from its sync source truncates its extra entries into a rollback file and rebuilds.
  • Read concern local returns the member's latest state; majority returns the state at that member's known commit point; linearizable works only on a primary and only if it can confirm a majority right now.
  • A causal session carries afterClusterTime; a member waits until it has applied up to that time before answering.
  • A retryable write carries (lsid, txnNumber); a primary that already has that pair in its replicated transaction table returns the stored result instead of applying again.
