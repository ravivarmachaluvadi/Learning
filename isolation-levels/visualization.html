Transaction isolation, one step at a time

Two Clerks, One Ledger

Two people change the same records at the same time. Each one does something completely reasonable. Put together, the books can end up saying something that was never true — and no error is raised anywhere. An isolation level is your choice about which of those endings the database is allowed to give you.

Below is the standard way to draw this: time runs down the page, one column per clerk. Step through it, then change the isolation level and watch the same actions end differently.

The four mechanisms

read uncommittedno locks, and you can see other people's unfinished work
read committedeach statement reads the newest committed data
snapshotthe whole transaction reads one frozen moment, and the first one to commit wins any clash
serializable
(tracking)		snapshot, plus bookkeeping about what was read — this is how Postgres does it
serializable
(locking)		no versions at all: locks, held to the end — this is how SQL Server and older engines do it

This models one integer per row, which is enough: every anomaly here is about when you see a value, never about what type it is. The engine is a direct port of the Java one in the lab, and both are checked against the same expected results.
