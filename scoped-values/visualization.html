The Binding Rail

A request carries context — who is calling, the request id — like a visitor badge: pinned on at the front desk, read by every room, taken off at the exit. This page steps through how Java's ScopedValue pins values to the call stack (watch the rail beside each stack), and how the older ThreadLocal badge gets rewritten and forgotten. What just happened

How to read it: each box column is one thread's call stack (top frame = currently running, marked in bold). The narrow column beside it is that thread's binding rail — with ScopedValue it holds exactly the badges pinned by the frames below it, so it can never disagree with the stack; with ThreadLocal it is a free-floating pocket that survives after frames pop, which is where every bug in these stories lives. A crossed-out badge is shadowed: temporarily covered by a rebinding lower in the stack. A red badge is stale: left over from code that already returned.
