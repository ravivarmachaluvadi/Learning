Why private copies exist

Each thread card shows a private copy row. A thread that reads an ordinary field is allowed to keep using the value it read the first time — the JVM may hold it in a CPU register and never look at memory again. That is legal, and it is why a write by one thread can stay invisible to another forever. Marking the field volatile, or reading it inside a lock, removes the private copy.

Nobody creates a thread per request forever

A thread costs about a megabyte of stack and a system call to create. So real Java servers keep a fixed crew of threads and feed them a queue of work. That single decision — how many workers, how deep a queue — is the most common production tuning knob in Java, and the most common way to hang a service. Set the numbers below and press play. Time is counted in ticks; a tick is one unit of work.

Doubling the crew roughly halves the wall clock — right up to the point where there is no work left to hand out. Past that, extra workers finish nothing sooner. In a real service they still cost memory and context switches.

This page is a model, not a JVM. Two honest simplifications: (1) each Java line is split into the machine steps that matter for the lesson, not the exact bytecode; (2) the private-copy row models stale reads as a cached value, whereas a real JVM usually produces the same effect by keeping the field in a CPU register and never re-reading memory. The observable consequence — a write that another thread never sees — is identical, and the Java Memory Model permits both. Everything else here (lock owner, entry set, wait set, notifyAll waking threads into the entry set rather than into the running state, compare-and-set failing and retrying) mirrors real synchronized and java.util.concurrent behaviour.
