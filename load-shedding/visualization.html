Predict before you run: at 60/s against a capacity of 50/s, what share of customers get an answer?

The arithmetic seems easy: 50 of every 60 can be finished, so about 83% should succeed and 17% should fail.

The measured answer is 0.7%. Not 83%. Under one in a hundred.

The queue grows by 10 requests every second and never shrinks. Within a minute everyone joining it is already certain to time out before reaching a worker — but the server never learns that, so it does all the work anyway. Run it and watch the two counters at the top separate.

The test that separates them

Nothing else changes. Capacity silently falls from 50/s to 10/s, and every setting you tuned is now wrong by 5×.

Predict: your queue cap of 20 is optimal today. A dependency gets 5× slower. What does it deliver?

The cap is still enforced. The config is unchanged and still looks right in code review. The rejection metric still shows it shedding hard.

It delivers 0.1% against a 16.7% ceiling — the same as having no shedder at all.

Twenty requests at 400 ms across four workers is 2,000 ms of waiting, which is twice the client's deadline. Every request it admits is already dead. Tick the box and run it, then try the same thing with CoDel, which measures time rather than counting.

Predict: at 3× overload with nothing rejected, what does switching FIFO to LIFO do?

It changes one word in the code. It rejects nothing, configures nothing, and adds no admission control. The baseline is 0.1% and the ceiling is 33.3%.

LIFO reaches 33.4% — the theoretical maximum. Median latency drops from 532 ms to 66 ms, and wasted work goes from 100% to zero.

The front of a backed-up FIFO queue is by definition the request that has been waiting longest, which is the one most likely to be dead already. FIFO under overload serves the corpses first.

But watch the queue-depth number. LIFO fixed goodput and did nothing about memory — the queue is still tens of thousands deep and still growing. That is why the real design pairs it with CoDel. Tick both and compare.

Predict: fractions of a fixed limit, at a perfectly healthy 35/s. What does it cost?

Nothing is wrong. The workers are 69% busy. There is capacity for every request.

It throws away 42% of the recommendation traffic anyway — overall 79.0% instead of 100% — because a quarter of a fixed limit of 12 is a hard limit of 3, enforced at all times.

Every figure on this page is produced live by a discrete-event simulator running in your browser — the same engine that produced every measured number in the lab's README.md. Before it was used for teaching it was checked against Little's Law, M/M/1, M/D/1, D/D/1, Erlang-C for M/M/4 and Kingman's approximation.

Runs are ten minutes of simulated time on a single fixed seed, so the same settings always give the same answer. The README.md quotes the mean of five seeds, so a figure here will usually sit within a point or two of the one written down rather than matching it exactly — at loads close to capacity a single run genuinely scatters. This is a model of an overloaded service: it demonstrates the lesson's mechanism, and it is not a claim about how any specific product behaves.
